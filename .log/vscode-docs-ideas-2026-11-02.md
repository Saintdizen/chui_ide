## 1. Главное в документе

VS Code в 2026 переопределил себя как AI-native editor: ядро — не редактор, а агент.
Три идеи, которые у них несут вес и которых у нас нет системно:

1. **Контекст — инженерия, а не автодополнение.** Отдельные статьи
   `agents/concepts/context` и `agents/guides/context-engineering-guide`: явные
   правила, что кладётся в окно и в каком порядке, и панель, которая *показывает*,
   чем окно занято.
2. **Настройка агента файлами, а не настройками UI.** `copilot-instructions.md`,
   `AGENTS.md`, `*.instructions.md`, `*.prompt.md`, `*.agent.md`, `SKILL.md`, хуки —
   всё лежит в репозитории, едет с проектом и ревьюится как код.
3. **Агент — среда исполнения, а не чат.** Артефакты, канвасы, автоматизации:
   агент запускает работу сам, человек смотрит и одобряет.

## 3. Предложения — по убыванию отношения «польза / работа»

### A. Контекст прогона: видимость и правка правил

**A1. Инспектор контекста** (статья `agents/concepts/context`).
У нас уже считаются `usage`, есть `context-fit` и `token-calibration`, но человек
не видит, **из чего** сложился ход. Статья прямо описывает такую панель.
Наш вариант: разложить по частям системный промпт / правила / вложенные файлы /
`#codebase` / `#diff` / память / историю, с токенами и кнопкой «убрать». Данные уже
собраны в `ChatRunLog`.
*Работа: средняя. Польза: высокая — сейчас это чёрный ящик.*

**A2. Правила проекта отдельным файлом** (`agent-customization/custom-instructions`).
Наша память проекта живёт в `.chui_ide` через `mind`. Разница существенна: память —
то, что агент *записал*; правила — то, что человек *закоммитил*. Предлагаю
`AGENTS.md` в корне (или `CHUI.md`): читается в каждый ход, ревьюится как код,
приоритет выше памяти.
*Работа: малая. Польза: высокая.*

**A3. Заготовки промптов** (`agent-customization/prompt-files`).
У нас есть `CONTEXT_COMMANDS` (`#codebase`, `#diff` и т.д.) — это статические
источники контекста. У них `*.prompt.md` — **параметризованные заготовки**: файл
с `${input}`, вызов из чата. Хорошо дополняет: `#diff` даёт данные, заготовка даёт
*задание*. Формат близок к нашему markdown-рендереру.
*Работа: средняя. Польза: средняя, наращивается дёшево.*

**A4. Хуки агента** (`agents/reference/hooks-reference`).
События вокруг инструментов: до/после вызова, до отправки. У нас есть `tool-policy.ts`
(разрешения) и `chat-approvals.ts`. Хук — пользовательская проверка поверх политики:
скрипт решает, пускать ли действие, или дописывает вывод. Ценно для «не пускать
`rm -rf`, `git push`» на уровне проекта.
*Работа: средняя (две точки вызова + запуск скрипта). Польза: средняя.*

### B. Git — дыры относительно `sourcecontrol/*`

**B1. Редактор трёхстороннего слияния.** У нас `conflict-view.ts` и
`disk-conflict.ts`, но 3-way merge-редактор (base/ours/theirs, «принять оба»,
пере-слияние) — основное, чего не хватает при конфликте.
*Работа: большая. Польза: высокая тем, кто сливает ветки в IDE.*

**B2. Пошаговый stage (по кускам) в панели изменений.** `chat-changes.ts` принимает
файл целиком; гит-раздел описывает staging по hunk'ам. Половина работы уже есть
в `diff-view.ts`.
*Работа: средняя. Польза: высокая в повседневном коммите.*

**B3. Quick diff — изменения относительно HEAD прямо в gutter.**
`editing/*/quick-diff`. У нас есть `history.ts` и diff-view, но в редакторе
изменённые строки не помечены. Считать можно уже готовым LCS.
*Работа: малая-средняя. Польза: высокая, дешёвая.*

### C. Агент как среда

**C1. Артефакты прогона** (`agents/run/artifacts`).
Сгенерированный отчёт показывается отдельной панелью, а не сообщением в чате.
У нас `agent-present.ts` и инструмент `show` — тот же смысл, но без постоянного
места. Дать артефактам панель рядом с редактором.
*Работа: малая. Польза: средняя.*

**C2. Субагенты** (`agents/run/subagents`).
Вложенный вызов агента с отдельным контекстом и своей задачей (поиск, ревью).
У нас `runTool` один и однопоточный. Механизм небольшой, но цена: токены удваиваются,
нужен жёсткий лимит глубины. Браться, когда упрётся: «поищи по всему проекту и не
забивай контекст».
*Работа: средняя. Польза: высокая на больших репозиториях, риск тот же.*

**C3. Автоматизации** (`agents/run/automations`) — запуск задачи по событию
(расписание, изменение файла). Почти `jobs.ts`. Не приоритет.

### D. Точечное из `configure/*` и `debugtest/*`

| Идея | Оценка |
|---|---|
| Синхронизация настроек (`configure/settings-sync`) | `.chui_ide` и так переживает перезапуск; между машинами — отдельный сервис, не сейчас |
| Профили (`configure/profiles`) | Ниже приоритет: воркспейсы уже несут конфиг |
| Локализация UI (`configure/locales`) | Механизм прост, но переводить весь UI — большая работа, ценность внешняя |
| Голос (`configure/accessibility/voice`) | Интересно, но внешний STT; проверять отдельно |
| `tasks.json` (`debugtest/tasks`) | У нас `src/main/node/{lint,format,tests}.ts` зашиты; чтение `tasks.json` даст совместимость с чужими репозиториями |
| Проброс портов (`debugtest/port-forwarding`) | Серверы в терминале есть; автопроброс — небольшой выигрыш |
| Скриншоты из браузера | `browser` есть; снимок страницы — малая работа |

## 4. Что взято первым

Разложено по частям `TASKS.md`: части 5–8 (чат, git, агент как среда, совместимость).
Порядок там же — в «Плане»: quick diff → staging по блокам → ревью правок агента →
инспектор контекста → проброс портов.

При сверке с кодом два пункта оказались уже сделанными и в TASKS не попали:
**правила проекта** (`workspace-context.ts:22` — `INSTRUCTION_FILES` уже читает
`AGENTS.md`/`CHUI.md`/`.ai_rules`/`CLAUDE.md`) и **staging по hunk'ам в gutter**
(`stageHunk`/`discardHunk` + меню полоски в `gutter-menus.ts`).
