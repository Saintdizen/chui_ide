## Скорость (осталось)

- [ ] **Установка зависимостей в CI — 21–23с в каждом из трёх заданий.**
       Замер 24.10: кешировать нечего кроме самого `node_modules` — `.vite` и
       `.vitest-cache` весят 48 КБ и переписываются каждый прогон (холодный старт
       37.7с против тёплого 37.65с). Остаётся `actions/cache` по хешу
       `package-lock.json` с ключом, включающим ОС: нативный `node-pty` переносится
       между ОС только с оговорками, а испорченный кеш дороже 23с. Проверять на ветке.

- [ ] **`tests/git-service.test.ts` — 7.2с, дальше не режется.** Замер стоимости
       самого git: один `commit` ≈ 10мс, `init --template=` — 5мс (шаблон убран, см.
       ниже), подмодуль — 68мс на `submodule add`. Итого почти всё время — 63 сцены
       по 5–15 git-вызовов. Резать дальше можно только числом сцен, а не настройкой.
       Проверено: `GIT_TEMPLATE_DIR` в env приложения (см. ниже) — 1.3мс на `init`,
       1мс на `commit`, размазано по всем git-вызовам. Дальше не режется.

- [ ] **Скорость Windows: разброс между прогонами ±30с съедает любой выигрыш.**
       Замер по одним и тем же шагам: тесты 104с (прогон `baec783`), 130с (`fcd1bcb`),
       123с (`916d361`) — при неизменном наборе тестов и одном раннере. Значит,
       сравнивать «до/после» по одному прогону нельзя: нужен либо повтор один за
       другим, либо счётчик тестов внутри. Убрано и подтверждено дважды:
       `fs.watch(recursive)` на корне проекта с 885 МБ `node_modules` включается
       380–440мс на каждое `open` (на `/tmp` — 1мс, на 300 файлах — 21мс), а тесты
       звали `open(process.cwd())` без нужды. Искать тем же приёмом:
       `grep -rn "\\.open(process.cwd())" tests` и `fs.watch` в тестах — сейчас пусто.
       Дальше — по снятию времени по файлам.
       Инструмент готов: `scripts/test-time-census.ts` — гоняет vitest с
       `--reporter=json` N раз и печатает по каждому файлу время во всех прогонах,
       среднее и разброс, плюс список «гуляет сильнее всего».
       **На Windows им ещё не мерили — нужен прогон на самом раннере**, Linux-замер
       к нему не относится: там 459 файлов дают 41.7 / 41.9 / 41.7с (±0.5%).
       Побочная находка того же замера, полезная и здесь: сумма времени всех файлов
       12.5с при прогоне 41.7с — то есть 70% прогона это импорт, трансформация и
       старт воркеров, а не сами тесты.

- [ ] **`tests/debug.test.ts` — 5.0 → 3.5с, дальше не берётся дёшево.** Замер:
       почти весь остаток — старт фейкового DAP-процесса (~150мс) и ожидание
       объявления потока в 28 тестах. `waitPhase` уже опрашивает каждые 2мс (было
       25мс, дало 0.4с). Прогрев адаптера в `fakeService` (поднять процесс раньше,
       пока тест собирается) **проверен и откачен**: сервис объявляет фазу
       `starting` ещё до `start()`, и 13 тестов ловят не ту фазу. Чтобы взять
       остаток — только перевод сцен на событие вместо опроса (не таймаут).
       **Откачено и проверено 24.10:** «ждать не фазу, а сам `pause()`» — не работает,
       `pause()` возвращается раньше, чем приходит событие `stopped`: фаза в этот
       момент ещё `running`, и тест падает в 3 прогонах из 3.

## Структура (долгая правка, отдельной сессией)

- [ ] **`src/main/ai/agent-tools.ts` — 2 471 строка (было 4 992).** Терминал,
       `edit`, `run_tests`, распознавание команд, правила подтверждения, бюджет
       вывода и контекст инструментов вынесены: `agent-terminal.ts`,
       `agent-edit.ts`, `tool-command.ts`, `tool-rules.ts`, `output-budget.ts`,
       `output-trim.ts`, `tool-context.ts`, `agent-lookup.ts`. Осталось в нём:
       реестр `runTool` и сами инструменты `read`/`search`/`lsp`/`checks`/
       `browser`/`web`/`mind`. Следующий шаг — `read`+`search` вместе (общий
       обход файлов и покрытие диапазонов), затем `lsp`+`checks`. Дальше не резать
       без повода: выигрыша в скорости нет, только читаемость.

- [ ] **`src/main/git/git.ts` — 2 397 строк (было 2 464).** Вынесен
       `git/exec.ts` (123 строки): запуск git (`execGit`), запуск клиентов
       площадки (`runForge`), их таймауты, `MAX_BUFFER`/`MAX_DIFF_BYTES` и
       пустой каталог шаблонов. 73 `this.exec` и 17 `this.forgeRun` стали
       импортом; в классе остался один прямой `execFile` (обновление индекса и
       подсчёт чужих правок). Шов проверен: 464 теста git, полный набор 5584.
       **`src/main/git/git.ts` — 132 метода** в одном классе
       `GitService` (forge, bisect, worktree, подмодули, коммиты). Замер 24.10:
       дробление здесь — не вынос файлов, а разбор класса. Каждый метод зовёт
       `this.run(` и приватные помощники того же класса, поэтому вынос требует
       явной зависимости (объект с `run`), то есть рефакторинга с правкой вызовов.
       Выигрыша в скорости не будет — только в читаемости. Затевать, когда есть
       повод (править bisect или forge), а не «ради размера»: `src/shared/api.ts`
       лёг на тот же аргумент. Под зелёными тестами, по одному модулю за раз.

- [ ] **`src/main/ai/service.ts` — 2 594 строки (было 2 694).** Вынесен
       `workspace-context.ts`: карта проекта, память и правила проекта для
       системного блока плюс `versionOf` для сверки памяти чтений. Шов проверен
       сверкой: собранный блок совпал со старым байт в байт. Дальше резать
       нечем без повода: агентный цикл, шаг стриминга и сборка `ToolContext`
       сидят на одном состоянии диалога — их вынос будет переездом строк, а не
       разрезом. Кандидат на вынос по частям — перенос покрытия чтений
       (`coveredRequest`/`rememberRead` и разметка сомнительных строк, ~200 строк).
