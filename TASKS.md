Вне класса уже всё, что проверяется отдельно (`workspace-context.ts`,

Без повода не затевать: выигрыш здесь только в читаемости, скорость и поведение те же.

- [ ] **`src/main/git/git.ts` — 980 строк.** Распил идёт по одному узлу за
       сессию, методика та же, что на `agent-tools.ts`: grep частоты `this.X(` по
       блоку, брать узел с МАЛОЙ зависимостью от состояния класса. Вынесено так:
       `exec.ts` (запуск git и forge), `forge.ts` (413 строк — задачи, конвейеры,
       уведомления; `ForgeContext` из четырёх методов: `root`, `repositoryRoot`,
       `remotes`, `refresh`), `bisect.ts` (90 строк; `BisectContext` из трёх:
       `root`, `refresh`, `gitPath`), `inspect.ts` (61 строка — `headText`,
       `revert`, `reset`; `InspectContext` из трёх: `repositoryRoot`, `requireRoot`,
       `refresh`), `status.ts` (140 строк — разбор porcelain=v2, `repositoryMetaDir`,
       `writeLocalConfig`; ровно ноль обращений к состоянию класса, поэтому резалось
       без контекста вовсе).
       **Узел кончился, и это замерено.** Оставшиеся блоги (watcher, index/status,
       ветки, worktree, подмодули, личность и ключи) имеют 25–36 вызовов
       `this.repositoryRoot`/`this.requireRoot` на блок — это не узел с малой
       зависимостью, а сам класс. Дальше только вынос `GitService` целиком на
       составные сущности с явными зависимостями, то есть одна длинная правка на
       весь файл. По объёму она тоже ничего не даст: `inspect.ts` сократил git.ts
       на 0 строк (2010 → 2011) — выигрыш был в том, что правила легли в одно
       место, а не растворились в двух тысячах строк.

       **Поправка 26.10: «узел кончился» оказалось неверным.** После него файл
       ушёл 1 001 → 980, и оба шага были механическими: `readStatus` переехал к
       `parseStatus` (запуск git рядом с разбором его формата — 1 001 → 998), а
       `resolveRepositoryRoot` — в `exec.ts` (998 → 980). Урок методики: считать
       вызовы `this.X(` без разбора, ЧТО этот `this` — `repositoryRoot` и
       `requireRoot` после выноса источника правды в `exec.ts` перестали быть
       состоянием класса и стали чистой функцией от `root()`. Перед «это сам
       класс» — проверить, не стоит ли под обёрткой функция.

## Дальше по git.ts (записано 26.10, не сделано)

- [ ] **Конфликты одним куском — `conflict.ts` (~100 строк).** `markResolved`,
       `merge`, `rebase`, `reset` и операции конфликтов по пути. Все идут через
       `StatusContext` и НЕ трогают watcher — единственный оставшийся кусок, где
       вынос не требует решения про кеш статуса. Проверка: `npm run check:static`
       и полный `npm run test` (конфликты покрыты в `tests/git-*`).
- [ ] **`worktreeAdd`/`worktreeRemove`.** `WorktreeContext` (три метода) уже есть,
       тянет `gitPath`. Мелочь на 20–40 строк, отдельного коммита не стоит —
       приклеить к следующему крупному выносу.
- [ ] **Ядро: `status`/`refresh`/`publish`/watcher — НЕ вынос, а решение.**
       Тут кеш статуса и рассылка `GitChanged`; watcher зовёт `refresh`, а
       `refresh` зовёт `watcher.sync` — обратная связь. Рвать цикл можно только
       внедрением событий (watcher сообщает «изменилось», хозяин кеша решает, что
       пересчитать). Прежде чем браться, замерить, сколько стоит пересчёт статуса
       без кеша на большом репозитории: если дёшево — кеш не нужен вовсе и вопрос
       снимается, если дорого — нужен явный владелец кеша с очередью.
- [ ] **`git-context-source.ts` — источник «божественного» интерфейса.** 7
       колбэков, а `contexts.ts` собирает контексты через `extends`. Модуль,
       которому нужен только `root`, структурно получает `refresh`, `gitPath`,
       `remotes`: TypeScript прощает лишнее, поэтому «модуль не может позвать
       то, чего не просил» — правда только на бумаге. Проверка изоляции: убрать
       из конкретного `*Context` лишние поля и посмотреть, что сломается —
       сейчас не сломается ничего, и это и есть цена.

## Скорость (ждёт повода)

Повод — прогон CI дольше 2 минут (Windows-шаг «Тесты» сейчас ≈1м28с).
Замеры 25.10: повтор набора репозитория снят — `git-forge-success` 1.9 → 1.25с

дописью в `.git/config`).

- [ ] **`tests/git-service.test.ts` — 6.1с, потолок замерен.** Ревизия сцен
       сделана: пять читающих сцен переведены на готовый снимок (`readOnlyRepo`),
       три сцены про `pull` — на один хелпер, у `makeRepos` появился хук
       `afterClone`. Итог — **было 6.14с, стало 6.47с, то есть хуже на 5%**
       (3 прогона до и после, сумма времени сцен по JSON-отчёту). Причина
       названа, а не угадана: `readOnlyRepo` делает КОПИЮ снимка (`clone
       --no-hardlinks`) ради изоляции, и копия стоит дороже того `init`+`clone`,
       которую заменяет. Трогать `readOnlyRepo` без нужды нельзя — он держит
       изоляцию сцен друг от друга. Режется только число сцен: 22 из 63 меняют
       состояние, 41 читают, и дублей по набору вызовов нет — каждая проверяет
       свой метод. Дальше только смысл тестов, не настройка.

       инструмент ростера. Если жалоб нет — пункт закрыть, не тратя токены.
       Наследие п.дедупа: схема и подсказка уже не дублируют «абсолютный» —
       в схемах этого слова нет вовсе (проверено 26.10), экономить нечего.
