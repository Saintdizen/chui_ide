# Что предстоит

Только то, что реально сделать. Сделанное живёт в README и в тестах, доводы
прошлых решений — в комментариях кода и в переписях `scripts/`.

Снято разведкой 24.10 и уточнено её же замерами: у каждой задачи есть адрес
в коде и способ проверки, у каждого отказа — цифра. Раздел «сделано» здесь не
живёт (правило этой же шапки): доводы — в телах коммитов, поведение — в тестах.

## Скорость (осталось)

- [ ] **`npm ci` на Windows — 22.7с против 12.0с на Linux при том же числе пакетов.**
       Опись Linux (24.10): сеть 4.5с, установочные скрипты 1.1с, распаковка 382
       пакетов ≈6с — это предел секунд на этой машине. Замерить `npm ci --offline`
       на Windows с пустым кешем против тёплого: если дело в NTFS и антивирусе
       раннера — предел.
       Не повторять (снято замером): `.md`/`.rst` внутри `node_modules` `tsc` не
       тормозят — 11.19с до чистки 105 файлов, 11.40с после (864М → 863М).

- [ ] **`debug.test.ts` 5.0с + `node-debug.test.ts` 4.1с — 16% прогона, и это живой
       запуск адаптеров, а не церемония вокруг.** Опись по двум прогонам одинаково
       показывает: `node-debug` (4.1с) весь построен на настоящих `spawn('node',
       ['--inspect=…'])` — это и есть проверяемое. В `debug.test.ts` 35 вызовов
       `fakeService()`/`tcpPythonService()`, каждый заводит `mkdtempSync` + `writeFileSync`,
       то есть ~500мс на папки. Заманчиво кешировать скрипт адаптера — и вот почему
       НЕЛЬЗЯ (снято на живом коде 24.10, три подхода, все легли):
         (1) кеш по режиму stdio/tcp — 17 проверок падают по таймауту. Скрипт читает
             `process.env.FAKE_DAP_FRAME` при СТАРТЕ, а тест на симлинки меняет
             переменную уже после `new DebugService`; прочитанный раньше времени кадр
             пуст, и «stopped» не наступает;
         (2) вшить задержку потока в текст скрипта — падает проверка «пауза не
             теряется» с `threadDelayMs: 250`: число берётся из `process.argv[2]` на
             каждый запуск, а вшитое фиксировано;
         (3) вшить только задержку, оставив `FAKE_DAP_FRAME` живым — то же самое:
             `Number('__THREAD_DELAY__')` даёт NaN, и `setTimeout(…, NaN)` = 0.
       Остаётся одно, что кешем не ломается: `dirs` не тянет `rmSync`, папки копятся
       до конца процесса. Если брать дальше — с выносом фабрики в отдельный модуль и
       честной границей «что можно кешировать» в комментарии, а не подгонкой якоря.

- [ ] **`tests/git-service.test.ts` — 7.2с, дальше не режется.** Замер стоимости
       самого git: один `commit` ≈ 10мс, `init --template=` — 5мс (шаблон убран, см.
       ниже), подмодуль — 68мс на `submodule add`. Итого почти всё время — 63 сцены
       по 5–15 git-вызовов. Резать дальше можно только числом сцен, а не настройкой.
       Проверено: `GIT_TEMPLATE_DIR` в env приложения (см. ниже) — 1.3мс на `init`,
       1мс на `commit`, размазано по всем git-вызовам. Дальше не режется.

- [ ] **Скорость Windows: шума нет, есть один файл.** Мерили на самом раннере 24.10
       (`scripts/test-time-census.ts`, 2 прогона подряд): 114.7с и 114.6с, сумма
       времени файлов 204068 / 202405 мс — разброс 0.8%, «гуляет сильнее всего» пусто.
       Прежние «±30с» были сравнением РАЗНЫХ прогонов на разных раннерах, а не шумом.
       Сумма файлов ≈203с при прогоне 115с: файлы идут параллельно, загрузка ~1.8×.
       Главная статья одна: `tests/git-service.test.ts` — 72.5с из 203с (на Linux 8с).
       Резать дальше патчами не выходит: проверено, что выигрыш дают только
       `-c safe.directory=*` в этом файле и сокращение числа git-запусков (разобрано
       в коммитах), а точить процессы бессмысленно: `execFile` держит процесс 7.6мс
       (528 запусков / 4.0с), латентность самих процессов 5.3мс, потолок — 528 × 7.6мс.
       Отказано проверкой (с цифрами, чтобы не возвращаться): клон «снимка» под кэш
       (`--shared` 1.5мс против 1.4мс), пакетная история (20-22мс против 15-17мс),
       два `git init` одним процессом (берёт ровно один каталог), `push <адрес>`
       вместо `push origin` (`remote.origin.*` не создаёт), общий bare-снимок для
       `readOnlyRepo()` (инвариантен к bare — кэшировать нечего, 8.65с против 7.69с).
       Остаток Windows — только числом сцен (на Linux 70% прогона — импорт,
       трансформация и старт воркеров, а не тесты).

## Структура (долгая правка, отдельной сессией)

- [ ] **`src/main/ai/agent-tools.ts` — 2 058 строк (было 4 992).** Вынесены
       `agent-context`, `agent-terminal`, `agent-edit`, `agent-list`, `agent-lookup`,
       `agent-read`: чтение одним файлом и пачкой, его потолки (строки, символы,
       бюджет вывода) и покрытие прочитанного. `readAction` — то, что в схеме одно
       имя, а внутри три формы (`paths`, `path`, ни одного). `agent-tools.ts`
       остался таблицей имён и аргументов.
       Следующий шов тот же по природе — `read` и `search` делят обход проекта:
       `findFiles` зовёт разбор маски и обход файлов из `agent-list`, `search` —
       тот же обход с потолком `MAX_SEARCH_HITS`. Свести обход в `agent-walk.ts`,
       оставив инструментам только формат ответа. Дальше — `lsp` + `checks` (оба
       про языковой сервер и отчёт).
       Так же, как раньше: искать узел замером частоты `this.X(`/`ctx.X` — вынос
       окупается там, где у функции мало зависимостей от остального файла.

- [ ] **`src/main/git/git.ts` — 2 397 строк (было 2 464).** Вынесен
       `git/exec.ts` (123 строки): запуск git (`execGit`), запуск клиентов
       площадки (`runForge`), их таймауты, `MAX_BUFFER`/`MAX_DIFF_BYTES` и
       пустой каталог шаблонов. 73 `this.exec` и 17 `this.forgeRun` стали
       импортом; в классе остался один прямой `execFile` (обновление индекса и
       подсчёт чужих правок). Шов проверен: 464 теста git, полный набор 5584.
       **`src/main/git/git.ts` — 132 метода** в одном классе
       `GitService` (forge, bisect, worktree, подмодули, коммиты). Замер 24.10:
       дробление здесь — не вынос файлов, а разбор класса. Каждый метод зовёт
       `this.run(` и приватные помощники того же класса, поэтому вынос требует
       явной зависимости (объект с `run`), то есть рефакторинга с правкой вызовов.
       Выигрыша в скорости не будет — только в читаемости. Затевать, когда есть
       повод (править bisect или forge), а не «ради размера»: `src/shared/api.ts`
       лёг на тот же аргумент. Под зелёными тестами, по одному модулю за раз.

- [ ] **`src/main/ai/service.ts` — 2 594 строки (было 2 694).** Вынесен
       `workspace-context.ts`: карта проекта, память и правила проекта для
       системного блока плюс `versionOf` для сверки памяти чтений. Шов проверен
       сверкой: собранный блок совпал со старым байт в байт. Дальше резать
       нечем без повода: агентный цикл, шаг стриминга и сборка `ToolContext`
       сидят на одном состоянии диалога — их вынос будет переездом строк, а не
       разрезом. Кандидат на вынос по частям — перенос покрытия чтений
       (`coveredRequest`/`rememberRead` и разметка сомнительных строк, ~200 строк).
