## Скорость (осталось)

- [ ] **Установка зависимостей в CI — 21–23с в каждом из трёх заданий.**
       Замер 24.10: кешировать нечего кроме самого `node_modules` — `.vite` и
       `.vitest-cache` весят 48 КБ и переписываются каждый прогон (холодный старт
       37.7с против тёплого 37.65с). Остаётся `actions/cache` по хешу
       `package-lock.json` с ключом, включающим ОС: нативный `node-pty` переносится
       между ОС только с оговорками, а испорченный кеш дороже 23с. Проверять на ветке.

- [ ] **`tests/git-service.test.ts` — 7.2с, дальше не режется.** Замер стоимости
       самого git: один `commit` ≈ 10мс, `init --template=` — 5мс (шаблон убран, см.
       ниже), подмодуль — 68мс на `submodule add`. Итого почти всё время — 63 сцены
       по 5–15 git-вызовов. Резать дальше можно только числом сцен, а не настройкой.
       Не проверено: `GIT_TEMPLATE_DIR=/dev/null` в env сервиса (тот же приём, но
       для самого приложения) — выигрыш ~1–2мс на вызов, размазан по всем тестам.

- [ ] **Скорость Windows: разброс между прогонами ±30с съедает любой выигрыш.**
       Замер по одним и тем же шагам: тесты 104с (прогон `baec783`), 130с (`fcd1bcb`),
       123с (`916d361`) — при неизменном наборе тестов и одном раннере. Значит,
       сравнивать «до/после» по одному прогону нельзя: нужен либо повтор один за
       другим, либо счётчик тестов внутри. Убрано и подтверждено дважды:
       `fs.watch(recursive)` на корне проекта с 885 МБ `node_modules` включается
       380–440мс на каждое `open` (на `/tmp` — 1мс, на 300 файлах — 21мс), а тесты
       звали `open(process.cwd())` без нужды. Искать тем же приёмом:
       `grep -rn "\\.open(process.cwd())" tests` и `fs.watch` в тестах — сейчас пусто.
       Дальше — только по снятию времени по файлам (`--reporter=json`, поле `duration`).

- [ ] **`tests/debug.test.ts` — 5.0 → 3.5с, дальше не берётся дёшево.** Замер:
       почти весь остаток — старт фейкового DAP-процесса (~150мс) и ожидание
       объявления потока в 28 тестах. `waitPhase` уже опрашивает каждые 2мс (было
       25мс, дало 0.4с). Прогрев адаптера в `fakeService` (поднять процесс раньше,
       пока тест собирается) **проверен и откачен**: сервис объявляет фазу
       `starting` ещё до `start()`, и 13 тестов ловят не ту фазу. Чтобы взять
       остаток — нужна другая логика ожидания (событие вместо опроса), а не таймаут.

## Структура (долгая правка, отдельной сессией)

- [ ] **`src/main/ai/agent-tools.ts` — 4 992 строки, 162 функции, 19 инструментов**
       в одном файле. Разнести по инструментам (`edit`, `run`/`terminal`,
       `browser`/`web`, `task`, `mind`, `lsp`/`checks`) с общим модулем контекста.
       По одному модулю за раз, под зелёными тестами.

- [ ] **`src/main/git/git.ts` — 2 464 строки, 132 метода** в одном классе
       `GitService` (forge, bisect, worktree, подмодули, коммиты). Замер 24.10:
       дробление здесь — не вынос файлов, а разбор класса. Каждый метод зовёт
       `this.run(` и приватные помощники того же класса, поэтому вынос требует
       явной зависимости (объект с `run`), то есть рефакторинга с правкой вызовов.
       Выигрыша в скорости не будет — только в читаемости. Затевать, когда есть
       повод (править bisect или forge), а не «ради размера»: `src/shared/api.ts`
       лёг на тот же аргумент. Под зелёными тестами, по одному модулю за раз.

- [ ] **`src/main/ai/service.ts` — 2 694 строки, 47 методов.** Разбирать после
       `agent-tools.ts` и по тем же правилам.
